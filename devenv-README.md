# devenv.sh dev environment for deephaven-server-docker

A reproducible `docker buildx` toolchain for this repo, built on
[devenv.sh](https://devenv.sh). Same shape as
`deephaven-base-images/devenv-README.md` — read that first if you haven't;
this file only calls out what differs.

## What's here

- **`devenv.yaml`** — inputs only, identical choice to
  `deephaven-core`/`deephaven-base-images` (`github:cachix/devenv-nixpkgs/rolling`).
- **`devenv.nix`** — no `languages.*` block; this repo's own build has no
  host-side compile step (every image is produced by `docker buildx bake -f
  <name>.hcl` against a `contexts/<name>/` directory). Provides:
  - `pkgs.docker-buildx` (pinned, currently 0.35.0) — symlinked into
    `~/.docker/cli-plugins/docker-buildx` at shell entry, only if nothing's
    already there.
  - `pkgs.jq` — for piping `docker buildx bake -f <name>.hcl --print`.
  - `pkgs.git`.
  - `DOCKER_HOST` auto-detection from a live rootless Podman socket
    (identical hook to `deephaven-base-images/devenv.nix`, itself copied
    from `deephaven-core/devenv.nix`'s `podmanDockerHostHook`) — never
    overrides an already-set `DOCKER_HOST`, never starts/configures the
    socket itself.
- **`.envrc`** — `eval "$(devenv direnvrc)"` + `use devenv`; run `direnv
  allow` once.
- **`devenv.lock`** — generated by devenv itself, analogous to `flake.lock`.
  Commit it; don't hand-edit.

## What's NOT here (deliberately)

- **No Docker/Podman provisioning.** Same stance as
  `deephaven-base-images/devenv.nix` — assumes a real Docker daemon (or
  Podman's Docker-API-compatible socket) is already running.
- **No cross-arch/QEMU emulation setup**, even though this repo (unlike
  deephaven-base-images) *does* build `linux/amd64` **and** `linux/arm64`
  when `MULTI_ARCH=true` or `RELEASE=true` (`.github/workflows/release-ci.yml`
  uses `docker/setup-qemu-action` for exactly this). Not provisioned here
  because the default local bake (`MULTI_ARCH=false`, `RELEASE=false`) only
  targets your machine's native platform — you only need emulation
  configured (e.g. `binfmt_misc`, or Docker Desktop's built-in
  Rosetta/QEMU integration) if you deliberately set `MULTI_ARCH=true`
  locally.
- **No deephaven-core JDK/Python toolchain**, even though `DEVELOPMENT.md`'s
  "custom sources" workflow depends on one (`./gradlew
  server-jetty-app:assemble py-server:assemble` in a *separate*
  deephaven-core checkout, before copying the resulting `.tar`/`.whl` into
  `contexts/server[-slim]/` here and running `DEEPHAVEN_SOURCES=custom
  docker buildx bake -f server.hcl`). That toolchain is
  `deephaven-core/devenv.nix`'s job, not this repo's — this file only
  covers what's needed once those artifacts already exist (or when using
  the default `DEEPHAVEN_SOURCES=released`, which needs none of this at
  all: sources come from a GitHub release tarball and PyPI wheel instead).
- **No `git-hooks.nix`, no `tasks.*`, no `services.*`.** Nothing in this
  repo's workflow has motivated any of these yet.

## Using it

Requires Nix (devenv is not self-bootstrapping): install it first, the
usual way for your platform. Then either:

```bash
# One-off, no persistent install:
nix run nixpkgs#devenv -- shell

# Or install devenv once, then just:
nix profile install nixpkgs#devenv
devenv shell

# direnv users, after the above:
direnv allow   # picks up .envrc automatically from then on
```

## Verified (2026-09-07, this branch's initial commit)

Ran directly via `nix run nixpkgs#devenv -- shell -- <cmd>` in this
workspace (no `docker` daemon running here — see caveat below), not just
inspected:

| Check | Result |
|---|---|
| `docker-buildx version` (standalone) | `github.com/docker/buildx v0.35.0` |
| `~/.docker/cli-plugins/docker-buildx` symlink created on shell entry | yes, points into the Nix store |
| `docker buildx bake -f server.hcl --print` | Full JSON for the `server`/`server-ui` tags, resolved correctly — confirms CLI plugin discovery works |
| `docker buildx bake -f server-base.hcl --print` | Same, for `server-base` |
| `jq --version` / `git --version` | `jq-1.8.2` / `git version 2.55.0` |
| `DOCKER_HOST` hook: no live Podman socket in this sandbox | stays unset, as expected |
| `DOCKER_HOST` hook: already-set value | left untouched |

**Not verified**: an actual image build, or the `DEEPHAVEN_SOURCES=custom`
local-dev path (needs a real deephaven-core build alongside it) — `--print`
only resolves and renders the bake file without needing a live daemon or
real source artifacts, which is why it was usable as the verification step
instead. Also not verified: `MULTI_ARCH=true`/cross-arch emulation, and the
live-Podman-socket case of the `DOCKER_HOST` hook — identical logic already
verified for `deephaven-base-images`/`deephaven-core`, not re-run here.
